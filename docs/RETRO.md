## 3. 架构决策复盘

### 3.1 做对了的

| 决策 | 理由与回报 |
|------|-----------|
| **Playbook-first，LLM 兜底** | 对比纯 LLM Agent：每次运行都是脉冲成本 vs 持续成本。沉淀机制让"花钱"只发生在页面变化的那一次 |
| **DOM 压缩 + ref 短 ID，非纯视觉坐标** | LLM 引用 `k23` 而非 (x,y)，规避视觉漂移；截图仍作双通道输入，语义 + 视觉互为校验 |
| **选择器 4 层 fallback（css→xpath→text→role/label）** | text 层可交互元素优先（button/a/input），修掉了"登录"匹配 h1 标题的经典坑 |
| **失败四分类 E1-E4 + EX** | 分类驱动行为：EX 配置错直接终止不触发兜底，E1 元素定位失败才是 Agent 主战场 |
| **恢复点评分制（URL 30 / selector 50 / text 20）** | 开发中发现设计缺口：assert-only 步骤 textContains 命中即 50 分，否则永远到不了阈值——设计评审时没看出来的边界 |
| **沉淀 css+text 双保险 + dialog:accept + 剥离 include** | v2 不是 Agent 轨迹的复读，而是蒸馏后的可维护 YAML；include 剥离避免登录二次展开 |
| **防失控三闸（接管 ≤3 次 / ≤15 步 / $0.10）** | Agent 失控的兜底成本上限明确，敢放进生产链路 |
| **请求级 LLM overrides** | Web 用户自带 Key 只活在请求内存，不污染服务端 .env——多租户前提 |

### 3.2 有代价的 / 不足的

| 问题 | 影响 | 反思 |
|------|------|------|
| 蒸馏只做"原位替换" | Agent 若绕路（多步迂回），v2 会比 v1 更长而不是更短 | v1.x 需要"轨迹最短化"：合并、去重、删除无效中间步 |
| 单进程内存版任务表（Web 后端） | 重启丢历史任务；并发无队列 | 演示够用，生产需持久化 + 队列。当时明确不为此加 DB，是对的 |
| 无真实站点验证 | 全部场景跑在自研 test-site | 改版模式是模拟的（按钮改名 + confirm），真实世界改版更杂（iframe/shadow DOM/懒加载）。**W9 已首试真实站点，暴露 3 个 bug，见 §8** |
| 恢复点窗口固定 5 步 | 大跨度改版（失败点与恢复点相距 >5 步）兜底后接不回去 | 可按失败步之后的步骤数动态扩展 |
| LLM 单模型依赖 | qwen3.8-max 网关抖动直接瘫痪 STATE B | CostTracker 已按模型分价，缺自动降级链（qwen3.8-max → glm-5.2 → deepseek-v4-pro） |

## 4. 数据与验收

### 4.1 成本模型实测（qwen3.8-max，单价 $1.6/$6.4 每 1M tokens）

| 场景 | LLM 调用 | Tokens | 成本 | 耗时 |
|------|---------|--------|------|------|
| STATE A 稳定运行（50 SKU） | 0 | 0 | **$0** | 22.6s |
| STATE A v2 沉淀后 | 0 | 0 | **$0** | 2.6s |
| A→B→A 自愈（demo-reprice） | 2 | 8,744 | $0.0417 | 112.9s* |
| 纯 Agent 全链路（登录+改价） | 8 | 15,438 | $0.0276 | 18.7s |
| 纯 Agent（Web 控制台提交） | 8 | 15,438 | $0.0276 | — |

*112.9s 中 Agent 仅 2 步，大头是感知器截图 + DOM 采集 + 思考型模型的 reasoning token（输出 5,772 > 输入 2,972，思考型模型输出贵 4 倍是成本主因）。

**结论**：一次自愈 $0.04 ≈ 等于 5 次 Starbucks WiFi，换回一条不再需要人工修的 Playbook。按"改版一次摊销"计算，LLM 成本可以忽略。

## 5. 踩坑精选（全量 27 见 SHARING.md）

按"通用可迁移"价值排序：

1. **zod discriminatedUnion 不接受任何 refine/z.lazy 包装成员** —— 跨字段约束必须放语义后置层；递归类型用 `Extract<Step, {action:'loop'}>` 派生而非显式注解。类型系统的问题 tsc 不报，运行时才炸。
2. **page.evaluate 传函数引用，模块作用域全 undefined** —— 函数体会被序列化到页面执行，必须自包含内联。连踩三次（主函数/常量/参数化调用）。
3. **Playwright 默认 dismiss confirm()** —— Agent 反复点"确认下单"看似成功实际被取消。`page.on('dialog', accept)` 一行解决，但排查了一小时。
4. **思考型模型连排输出双 JSON** —— `lastIndexOf('}')` 截取出 `{..}{..}` 无法 parse。改括号配对扫描（字符串转义感知）。
5. **单步批跑 Agent 每步重发完整上下文** —— 14s+/步。改 onAfterAction 钩子挂主循环，一次对话上下文内完成恢复点检查。
6. **vitest 默认 hookTimeout 10s** —— 多 chromium 并行挤爆 beforeAll，连环误报。全局 hookTimeout 120s + testTimeout 300s。
7. **zod default 丢失**：include 展开消费了原始 YAML 而非 parse 后数据。铁律：**有 default 的字段，下游必须消费 parse 后的数据**。
8. **真实站点三连坑（#25/#26/#27）**：导航销毁执行上下文、模型吐 DSML 而非 JSON、截图卡字体加载 30s。共同病根是**相信了默认行为**——凡跨外部资源或页面跳转的调用，一律显式超时 + 降级路径，且这类问题本地 test-site 一个都复现不了。

## 9. W10 补记：反爬对抗首战（2026-09-15）

**起因**：boss 要求"解决百度滑块验证"。W9 曾把它判为环境限制（动作集无拖拽），这次做了完整攻坚。

### 9.1 三层根因（都不是"没有拖拽"那么简单）

| 层 | 真相 | 怎么挖出来的 |
|---|---|---|
| 指纹暴露 | `navigator.webdriver=true`、UA 含 `HeadlessChrome`、`window.chrome` 缺失 | 探测脚本直接打印三项 |
| **首页 cookie 风控** | 冷启动直连 `/s?wd=` 正常；**先访问首页再搜索必被拦** | 三组对照实验（含复测） |
| 页面改版 | `#kw` 被 `.smart_input_superman .virtual-form{display:none}` 隐藏，可见输入框变为 `#chat-textarea` | 遍历 CSS 规则找命中项 |

**最反直觉的一条**：真凶是**首页 cookie**，不是指纹。被拦后 `clearCookies()` 再访问同一 URL 就恢复（7 条结果）——风控标记挂在 cookie 上，不挂 IP。**清 cookie 比换 UA 管用**。

### 9.2 四层修复

1. **预防·指纹**：新增 `src/browser/stealth.ts`，统一入口 `launchBrowser()` / `newStealthContext()` / `newStealthPage()`，三处 launch 全量接入（避免漏改导致行为不一致）。UA 按 `browser.version()` 动态生成
2. **预防·策略**：提示词规则 7——搜索站优先直接 goto 结果页，别碰首页搜索框
3. **自愈**：感知到验证码页 → `clearCookies()`（零 token）+ 提示 LLM 重新 goto，单任务上限 2 次
4. **能力**：新增 `drag` 动作，ease-out 曲线 + 抖动 + 随机停顿；drag 不进蒸馏（反爬对抗非业务流程）

### 9.3 结果与成本

百度搜索任务 **3 步 / 10.3s / $0.0038**，正确读出首条结果。对比 W9 的"4 步后判 fail"，从不可用变为可用。

### 9.4 沉淀的方法论

- **反爬问题先做入口路径对照实验**，再动代码。这次三组对照一次定位真凶，避免在指纹上瞎试
- **自愈优先用确定性手段**（清 cookie），不要用 LLM 猜——零成本、可预测、可复现
- **反爬结论易过期**（站点改版/风控升级）。代码注释里写清实测日期与结论，方便后人判断是否需要重验
- **反爬是军备竞赛**：本轮方案是"规避为主、自愈为辅"，不追求硬刚验证码。真要过图形验证码（百度的 `tuxing_v2` 是旋转图片类，非滑块）需要接打码平台，投入产出比不高，暂不做

## 10. W11 补记：容错的第一原则是"别让单点失败毁掉整条任务"（2026-09-17）

**起因**：真实使用中任务跑到第 5 步无声停止，报错只有 `LLM 返回空 content`。前 4 步（登录 → 进列表）全部正常，截图、轨迹、花掉的 token 全部丢弃。

**最有价值的点是：这不是模型的锅，是容错设计的洞。**

#26 那次已经加了"决策重试三层防御"，但重试循环长这样：

```ts
for (attempt of 1..3) {
  const raw = await chat(...);        // ← 在 try 之外
  try { return parseAction(raw.text); } catch { /* 重试 */ }
}
```

`chat()` 抛的错**完全绕过重试**，直接冒泡终止整个任务。防御只对"模型吐了坏格式"生效，对"模型什么都没吐"无效——**写了防御不等于覆盖了失败路径**，这是比空 content 本身严重得多的设计缺陷。

**四层修复**（详见 SHARING #29）：重试覆盖调用失败 + 每次重试换形态（加 token / 去 JSON 约束 / 去图片）+ 单步失败结构化退出（保留 steps 出报告）+ 失败调用也记账。

**三条沉淀**：

1. **容错要覆盖"调用"和"解析"两条失败路径**。写完重试先问：如果不幸的那一行抛错了，会被接住吗？
2. **重试要换形态，不要原地重复**。同样请求再发一次大概率同样失败。每次重试消除一个诱因（token 上限 / JSON 约束 / 图像输入）。
3. **单步失败不该让整条任务归零**。已执行的步骤和已花的钱都是资产，宁可"中止于第 N 步 + 明确原因"，也别抛异常。

**方法论补记**：偶发故障（真实 API 6 次探测全正常）**必须靠 mock 验证**。起一个能必然复现该故障的 HTTP mock 服务，才能确定性地证明容错逻辑生效——这次两个 Case（可恢复 / 持续失败）都是用 mock 验的，比等它偶发靠谱得多。

**成本视角的新认知**：`finish_reason=length` 的截断输出，网关**照样按 completion_tokens 收费**。之前只在成功返回时记账，导致 3 次失败烧掉 6000 tokens 却显示 `llmCalls=0`——**成本统计必须包含失败调用**，否则报表系统性偏低。

## 11. W12 补记：意图解析层 + 独立蒸馏（沉淀链路补全）

### 11.1 起因

一次架构答疑：老板质疑"沉淀为什么必须满足四个条件"，并给出他的设想——**成功就蒸馏，下次用 LLM 判断是否命中，命中就走沉淀**。追问过程中他还否掉了我提的 `hybrid` 路由策略（"换个语义还是无法正确执行，这策略意义何在"）。

两个追问都成立，最终收敛成一次架构补全。

### 11.2 三个关键决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 路由策略档位 | **砍掉 hybrid，只留 deterministic / intent** | 维度混淆：候选数量只影响解析成本，有无自由文本才决定是否需要语义理解。修正后默认值跟着入口走，用户不需要理解"策略" |
| 怎么省 token | **意图结果缓存，不是跳过解析** | 跳过解析 = 读不懂语义 = 回到原始问题。缓存 key = 归一化任务 + 域名，高频重复场景命中率接近 100% |
| 误命中风险 | **置信度阈值 + 执行后成功断言** | 安全模型从 fail-safe（误判→Agent 兜底→多花钱）变成 fail-dangerous（误判→静默执行错流程），必须补 |

### 11.3 实现

| 模块 | 职责 |
|---|---|
| `src/learner/draft.ts` | F-10 独立蒸馏：Agent 成功轨迹 → 全新 Playbook（自带 baseUrl/allowDomains/起始 goto/末尾成功断言），支持 LLM 语义化参数命名 |
| `src/router/intent.ts` | 意图解析层：一次 LLM 调用完成「选流程 + 抽参数 + 自评置信度」，含结果缓存（FIFO 200 条）与阈值判定（<0.7 走 Agent） |
| `server/index.ts` | `learnMode`（off/on-failure/on-success）+ `routeMode`（deterministic/intent），`/api/match?mode=intent` |
| Web | 主页与会话页：「失败自动沉淀」勾选 → 三档下拉；新增路由模式下拉；命中卡展示置信度与自动提取的参数 |

成功断言的实现取巧但有效：**沉淀时在末尾追加一个 `assert` 步骤**记录终态 URL path，下次执行不符 → assert 失败 → Playbook 整体失败 → **已有的 A→B 兜底机制自动接管**。零新增机制，复用现成链路。

### 11.4 成本模型变化

| 场景 | W11 及以前 | W12 intent 模式 |
|---|---|---|
| 命中沉淀 | ¥0（但读不懂语义） | ~¥0.002（解析）；命中缓存则 ¥0 |
| 未命中 | Agent N 步 ≈ 6600 tokens | 同左 + 解析开销 |
| 沉淀覆盖范围 | 单个 Playbook 的单步骤 | 任何 Agent 跑通的任务，跨流程复用 |

净省约 75%（省掉多轮感知循环，只付 1 次解析），换来的是跨流程复用与自然语言参数提取。

### 11.5 遗留

1. **独立轨迹库仍未建** —— 当前 `on-success` 沉淀直接写 `playbooks/` 主目录（立即可用，闭环可见），但产物仍与 Playbook 绑定，不是可独立检索的"轨迹"实体
2. **向量召回未接** —— 候选多时 prompt 会变长；`select.ts` 注释里预留的"候选 >200 条接向量召回"仍然空着
3. **成功断言只用 URL path** —— 未记录关键文本；终态未发生跳转的任务（如纯表单提交）拿不到有效断言
