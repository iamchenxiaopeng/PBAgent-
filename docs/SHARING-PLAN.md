## 1. 演讲定位

| 项 | 设定 |
|----|------|
| 受众 | 团队内部：前端/后端/测试工程师为主，可能有少量非研发 |
| 时长 | **40 分钟正式版**（30 讲解 + 8 演示 + 2 缓冲），附 15 分钟精简版结构（§8） |
| 形态 | 投屏幻灯（或全屏讲稿）+ **现场 Live Demo（压轴）** + Q&A |
| 目标 | 听完能复述三态模型；认可"脉冲式成本"这个反直觉结论；有人想试用 |

**一句话主旨**：
> 已知流程 $0 确定性执行，页面改版时花 4 分钱自愈一次，自愈路径自动沉淀——LLM 的钱只花在刀刃上。

**三个记忆锚点**（演讲中至少各重复两遍）：
1. **A→B→A→C** 四字母闭环（结构记忆）
2. **$0 / $0.0417 / $0.0026**（数字记忆：稳定跑、自愈一次、沉淀后重跑）
3. **"模拟环境验证架构，真实环境验证工程细节"**（方法论记忆）

## 2. 叙事弧线（为什么这么排序）

```
痛点（共鸣） → 洞察（反直觉） → 方案（四字母模型） → 实现（代码深度）
     → 数据（实测背书） → 演示（眼见为实） → 踩坑（真实感 + 笑点） → 方法论（带得走）
```

设计逻辑：
- **先讲钱再讲架构**：受众里不写代码的人也能跟上"成本反转"叙事，前 5 分钟不流失任何人
- **代码深度放在中段**：此时工程师的兴趣已被吊起，非工程师可以走神 5 分钟
- **演示放压轴不放开场**：演示是最大悬念，先给足铺垫（"讲了 8 步自愈，现在现场让它挂一次"）
- **踩坑故事收尾**：真实站点三连坑和百度反爬是全场戏剧性最强的部分，放后面留口碑

## 4. 演示环节编排（8 分钟，压轴）

### Demo 总原则
- **每个 demo 开跑后不停等**：边跑边讲下一步要做什么（Agent 模式每步 3-5s，正好填词）
- **每个 demo 有一个"看点句"**：跑之前告诉观众看什么
- **全链路只依赖本地服务 + LLM 网关**：不碰外网真实站点（百度反爬只讲故事不 live）

### Demo 1（2'）：零 LLM 确定性执行——"快得不像有 AI"
- 操作：Web 控制台主页 → URL `http://localhost:3456/login` + 任务"把 S050 的价格改成 199"
- 画面：匹配卡弹出 ⚡demo-reprice-v1（唯一候选零 LLM 命中）→ 参数框自动预填 price=199 → 确认执行
- 看点句：*"注意右上角的 LLM 调用数——全程是 0，成本 $0，10 步 3.4 秒"*
- 讲什么（跑的时候）：智能路由两层结构（域名硬过滤 → 单候选不花钱）

### Demo 2（3'）：A→B→A→C 完整闭环——"让它当众挂一次"
- 前置：把 demo-reprice 主文件换回 v1 旧选择器版（点"保存"，而页面改版后按钮叫"确认下单"）
- 操作（二选一，见 §5 增强①）：
  - **增强后（推荐）**：Web 端同 Demo 1 提交 → 第 8 步 E1 失败 → 界面上 Agent 兜底步骤出现 → 恢复点命中续跑 → 完成
  - **当前可用（CLI）**：`pbagent run playbooks/demo-reprice.yaml --takeover --learn --params '{"username":"demo","price":"222"}' --baseUrl http://localhost:3456`
- 看点句：*"第 8 步挂了——保存按钮改名叫'确认下单'了。看 Agent 怎么找到它，看它怎么接回主流程"*
- 收尾看点：跑完 `pbagent diff playbooks/demo-reprice.yaml` 展示 v2 diff（步骤级、人可读），讲"promote 之后下次又是 $0"

### Demo 3（2'）：会话式多轮追问——"第二轮只说一句话"
- 操作：在刚才的会话里直接输入"再把 S050 改成 333"（不填 URL）
- 看点句：*"我没填 URL——它记得这个会话里在哪个站点干活"*
- 讲什么：URL 继承 + 会话记忆注入（近 6 轮指令 + 上轮任务快照拼进提示词）

### 备用 Demo（时间富余 1'）
- `docs/assets/abac-timeline.html`：交互式四态时间线，点每个阶段看当时发生了什么（复盘 Demo 2 用）

### 演示前检查清单（开场前 10 分钟执行）
```
[ ] test-site 3456 / 后端 4567 / vite 5173 三服务存活（curl 各打一次）
```

## 5. 演示项目增强建议（①②③ 已交付，2026-09-16）

按投入产出比分档。**我的推荐：做 ①②③，约一天工作量；④⑤ 看时间；⑥ 不做。**

### ① 已交付：Web 端 Playbook 失败自动兜底 ✅
**现状缺口**：Web 端命中沉淀流程后走 `executePlaybookTask` → 纯 STATE A，失败直接 error 报结束。`runWithTakeover`（A→B→A 编排）只在 CLI 端。**最亮的闭环在 Web 界面演不了**，只能切终端演示，观感断裂。
**改法**：`executePlaybookTask` 的 catch 分支接 `runWithTakeover`（LLM 未配置时保持直接失败），B 段 AgentStep 经 toStep 转 SSE 推给前端时间线，learn 产物（v2 草稿）可选。
**收益**：压轴 Demo 2 全程在 Web 界面完成，"电影感"完整；顺带补齐产品功能（不只演示用）。
**风险**：与 #23 同类陷阱（请求体加字段两端同步），需要一条 e2e 兜底。

### ② 已交付：test-site 演示数据重置 ✅
`POST /api/reset` 把 SKU 价格重置回初值。保证连续两场演示数据一致，也避免"上次演示改过价导致断言差异"。
（低成本替代：每次演示用不同价格参数——但不如下面③脚本化来得稳）

### ③ 已交付：一键演示脚本 ✅
`bash scripts/demo.sh`：起三服务（存在则跳过）→ 调 reset → 校验 health/match → 打印演示清单和每个 demo 的操作步骤。现场不再手忙脚乱，也方便他人复用。
另有子命令：`use-v1`/`use-v2`（切换主 playbook 版本）、`status`（查服务与版本）、`restart`（改代码后重启）。

### ④ 可选：variant=c 二次改版（约 0.5 天）
v2 沉淀后再注入一版改版（如按钮挪位置 + 文案再变），演示"再挂 → 再自愈 → v3"，强化"军备竞赛也能赢"的螺旋叙事。
**代价**：演示时间 +2 分钟，版本链多一层（讲解负担），45 分钟版才建议上。

### ⑤ 可选：版本链 Web 可视化（约 1 天）
`/api/playbooks` 接口已有，前端加版本历史 + diff 渲染组件（数据源 `v{n}.diff.md` 现成）。演示"promote 前先看 diff"的治理流程更直观。锦上添花，非必需。

### ⑥ 不建议现场演示
- **百度反爬 live**：风控策略随时变（SHARING #28 已注明"结论易过期"），翻车率高。用 W10 实录截图 + 三组对照实验表讲故事，效果不降。
- **50 SKU 压测**：22.6s 的等待对观众是冷场，用数字讲（"209 步 22.6 秒 $0"）即可。

## 6. Q&A 预案（预计被问的 8 个问题）

| # | 问题 | 回答要点 |
|---|------|----------|
| 1 | 为什么不用 LangGraph / Agent 框架？ | 决策循环本质是"感知→决策→执行"三步 for 循环，530 行手写 vs 引入一坨依赖；纯提示词工程调试透明（每轮 LLM 输入输出可全文审计）；框架的图编排收益在多分支工作流，我们是单循环+钩子。当初设计文档确实写了 LangGraph，实现时砍掉了——DESIGN v1.1 已记录这个修订 |
| 2 | 和 Testim / mabl 这类商业方案比？ | 它们是 SaaS（数据出境 + 订阅制）、录制回放为主（无 LLM 语义兜底）；我们是私有部署 + Playbook 是人可读 YAML 资产 + 自愈沉淀闭环。不同赛道 |
| 3 | 为什么 DOM 优先而不是纯视觉（CUA）？ | DOM ref 短 ID 定位准、token 省一个量级；纯视觉坐标漂移是业内公认痛点。`AgentStep.engine` 字段已预留视觉通道分流位，DOM 失效场景（canvas/iframe 遮挡）是 v2 备选 |
| 4 | 恢复点误判怎么办？ | 评分制（URL+30/selector+50/text+20）+ 阈值 50 + **唯一最高分**才回归 + 5 步窗口。开发中还修过一个边界：assert-only 步骤上限 20 分永远过不了阈值，补了文本命中即 50 |
| 5 | LLM 会不会乱点危险按钮？ | 域名白名单（导航/提交全检查）+ 危险特征拒绝（删除/支付/清空）+ 防失控三闸（接管 ≤3 次 / ≤15 步 / $0.10） |
| 6 | 并发/多用户？ | 当前单进程内存任务表，演示够用；v1.x 路线：持久化 + 队列。不为此提前上 DB 是刻意的 |
| 7 | Playwright 自己不是有 selector 自愈吗？ | 它的自愈是"选择器层"的（getByRole 等），我们解决的是"流程层"：跨步骤的状态推进 + 失败后从哪一步接回去 + 自愈经验怎么留下来。两层互补 |
| 8 | 适合什么场景落地？ | 高频重复的 Web 批量操作 + 无 API 的内部系统（改价/对账/报表导出）。不适合一次性任务（沉淀没回报）和强验证码场景 |
