## 1. 项目背景

### 1.1 赛道背景：CUA 的成本困境

CUA（Computer-Using Agent，让 AI "看屏幕 → 推理 → 移动鼠标 → 点击"）是 2025-2026 年 Agent 落地的热点方向。但业界实践暴露出结构性问题：

| 维度 | 纯 CUA 模式的问题 |
|------|------------------|
| 成本 | 每一步都要调 VLM（截图 + 推理），一个 20 步任务 = 20+ 次多模态调用 |
| 速度 | 每步 3-10 秒（截图 → 上传 → 推理 → 动作），批量场景不可接受 |
| 稳定性 | 视觉定位漂移、坐标抖动导致同一任务今天能跑明天挂 |
| 确定性 | LLM 每次决策有随机性，无法满足"每天凌晨 3 点自动对账"这类审计要求 |
| 可审计 | 操作链路是黑盒，出问题无法回放定位 |

### 1.2 核心洞察（来自 AppliedLabs 的 Playbook-first 架构）

GitHub 上 AppliedLabsAI/cua 提出的 **Playbook-first** 思路：**已知用确定性脚本，未知才用 AI**。

- 已知流程 → 编写 **Playbook**（YAML 描述的操作流程），由 Playwright 确定性执行，**零 LLM 调用**
- 只有步骤失败时（元素找不到、页面改版）→ 切换到 **LLM Agent 兜底接管**
- Agent 完成恢复点后 → **回归 Playbook** 继续确定性执行
- Agent 跑完的路径可**自动沉淀为新 Playbook**，越用越快、越用越省

这是"专家系统 + 大模型兜底"的经典混合架构在浏览器自动化领域的落地，工程上可落地、成本可控、确定性有保障。

### 1.3 为什么是我们

- 团队有 Playwright 使用经验（数据平台 E2E 测试）
- 团队有 LangGraph JS 开发经验（设计稿转代码 Agent 项目）
- 有多模态 VLM 接入能力（Qwen-VL / GPT-4o）
- 内部存在大量"无 API 的内部系统"批量操作需求，是天然的第一批用户

### 1.4 竞品与参考

| 方案 | 定位 | Playbook | LLM 兜底 | 开源协议 | 启发点 |
|------|------|----------|----------|----------|--------|
| AppliedLabs cua | 生产级浏览器 Agent | YAML | 有 | AGPL | 直接对标原型，核心借鉴对象 |
| Browser-use | 通用网页 Agent 库 | 无（纯 LLM 驱动） | — | MIT | DOM 序列化喂 LLM 的做法 |
| Skyvern | 视觉驱动的浏览器 Agent | 无 | — | AGPL | 视觉 + DOM 融合定位 |
| Playwright codegen | 录制生成脚本 | 有（JS 代码） | 无 | Apache-2.0 | 录制→沉淀的交互范式 |
| Zapier/N8n | 通用自动化平台 | 有（私有格式） | 有（AI 步骤） | 商业 | 参数化、错误处理、调度生态 |

### 1.5 差异化定位

不做通用 CUA 平台，聚焦 **"高频重复的 Web 批量操作"**：

1. **Playbook 即资产**：一个流程一次录制，永久复用（直到网站改版）
2. **失败自动兜底**：Playbook 挂了不用人管，AI 接管修路径，跑完自动沉淀新版
3. **全程可审计**：每步操作有截图、有耗时、有结果，出问题可回放
4. **成本两个数量级优势**：目标是纯 CUA 的 1/20 以下

## 2. 产品目标

### 2.1 产品定位

一句话：**给"没有 API 的系统"装上低成本、可审计的自动化手**。

形态：Node.js CLI 工具 + 可选 HTTP 服务（后续版本可挂调度）。

### 2.2 目标用户与场景

| 用户 | 场景 | 频率 | 当前做法 |
|------|------|--------|----------|
| 运营/商务 | 内部后台系统批量操作（无 API） | 每天多次 | 人肉点几百下鼠标 |
| 电商运营 | 平台商品上架 / 批量改价 / 改库存 | 每天多次 | 人肉或雇人 |
| 数据分析 | 定期抓取需登录的网站数据（报表、行情、榜单） | 每日/每周 | 人肉导出 + Excel |
| 行政/HR | 自动填写各类 Web 表单（报销、审批、申报） | 每周 | 人肉填表 |
| 开发者 | 为老系统补自动化能力、做集成胶水 | 按需 | 写一次性脚本 |

### 2.3 成功指标（North Star & 护城河指标）

| 指标 | 定义 | 目标 |
|------|------|------|
| **成本优势比** | 同任务（纯 CUA 调用成本）/（PBAgent 总成本） | ≥ 20x |
| **无干预成功率** | 全程无人干预跑成功的任务占比 | ≥ 90%（单次运行） |
| **自愈率** | Playbook 失败后 LLM 兜底成功恢复的比例 | ≥ 70% |
| **Playbook 复用率** | 二次运行时 100% 走 Playbook（零 LLM）的比例 | ≥ 95% |
| 单步耗时（Playbook 模式） | goto / click / fill 类步骤平均耗时 | < 1.5s |
| Playbook 生成成本 | 录制一条新 Playbook 的 LLM 成本 | < $0.10 |

### 2.4 分期目标

- **MVP（4 周内）**：内部可用。CLI + 核心 YAML + 确定性执行 + 失败检测与截图归档（Agent 兜底接管在 v1.0 交付）。
- **v1.0（8 周内）**：内外可分享。兜底 Agent + 恢复点回归 + 新 Playbook 沉淀 + 成本统计 + 演示站点 + 分享文章。
- **v1.1+（3 个月+）**：生态化。Playbook 市场、任务调度、免登录制、Playbook 存储后端、多人协作。

## 3. 方案对比（对外分享的核心论点）

### 3.1 三种方案对比表

| 维度 | 纯 Playwright 脚本 | 纯 CUA（全 AI） | **PBAgent 混合方案** |
|------|--------------------|-----------------|---------------------|
| 单任务成本 | ~$0 | $0.5+（20步 × 25次调用） | ~$0.02（兜底 1-2 次接管） |
| 执行速度 | 秒级、最快 | 慢（每步 3-10s） | 秒级（兜底段慢） |
| 稳定性 | 高，但**网站改版即挂** | 低，视觉漂移 + 随机决策 | **高**：挂了有 AI 修，修好回归脚本 |
| 确定性/可审计 | **强**（代码可 review） | 弱（黑盒） | 强：脚本段可 review，兜底段有轨迹 |
| 开发成本 | 高（每个流程手写代码） | 低（自然语言描述即可） | **低**：跑一遍自动生成 |
| 维护成本 | 高（改版需人肉修脚本） | 无脚本但每次都贵 | **低**：改版时 AI 自愈并沉淀新版本 |
| 适合场景 | 流程稳定不变的内部系统 | 一次性、探索性任务 | **高频重复 + 偶尔会变的长尾系统** |

核心结论：**纯脚本便宜但脆，纯 CUA 灵活但贵，混合方案用 1/25 的成本拿到接近纯脚本的确定性。**

### 3.2 三态运行模型（产品核心心智模型）

产品有三个运行态，用户只需要理解一个规则：**脚本挂了，AI 顶上；AI 修好，回归脚本**。

- **STATE A — Playbook 执行态**：默认态。YAML 步骤 → Playwright 确定性执行。零 LLM、秒级、可审计。
- **STATE B — LLM Agent 接管态**：任一步骤失败即进入。视觉（截图→VLM）+ DOM 双通道分析页面，逐步决策，直到到达恢复点或任务完成。
- **STATE C — 沉淀态（Learning）**：接管段结束后触发。把 Agent 轨迹 → 新 YAML 步骤 → Playbook 新版本（diff 可 review 可回滚）。

状态迁移：A→B（步骤失败）、B→A（到达恢复点）、B→C（任务完成）、C→A（用新版重跑）。

### 3.3 典型场景案例（MVP 演示剧本）

**场景 1：内部后台批量改价（主打场景）**
> 运营同学要给 50 个 SKU 改价格。原来人肉在后台一页页点、改、存。现在一条命令：
> `pbagent run ./playbooks/reprice.yaml --params '{"ids":[...50个], "price": 99}'`
> 50 个 SKU 全部走 Playbook 确定性执行，全程 LLM 调用 0 次，耗时 3 分钟，成本 $0。第 17 个 SKU 页面因为 A/B 实验改了按钮位置，Playbook 失败 → LLM 接管 → 找到新按钮 → 完成操作 → 回归 Playbook → 自动沉淀 v2 版本。下次运行直接用 v2，又是零 LLM。

**场景 2：定期抓取需登录网站数据**
> 每天早上 8 点抓取某供应商门户的库存报表：登录（Playbook 持久化 session）→ 导航到报表页 → 设置日期筛选 → 导出 Excel → 下载到指定目录 → 落盘命名 `库存报表_2026-09-08.xlsx`。Playbook 一年不挂，就一年不花一分钱 LLM 费。

**场景 3：自动填表**
> HR 每月为新员工批量提交入职表单：姓名/身份证/银行卡 30+ 个字段，一条 Playbook 参数化循环搞定。

### 4.2 P0 功能详细需求

#### F-01 Playbook YAML 解析与校验

- 支持描述"打开 URL→点击→填表→提交→提取结果"的完整流程
- 加载时做 Schema 校验（结构、字段类型、选择器格式），校验失败给出**可操作的错误提示**（行号 + 修复建议）
- 支持 `include` 复用子流程（如"登录"子 Playbook），避免每个流程重写登录步骤
- 支持对读者友好的 `description` 字段，`pbagent validate` 命令可打印流程摘要

验收标准：
- [ ] 合法 YAML 100% 正确解析
- [ ] 10 类常见非法 YAML（缺字段、类型错误、选择器格式错误）全部给出带行号的错误提示
- [ ] include 循环引用检测（A include B，B include A → 报错）
- [ ] 校验 500 条 Playbook 的平均耗时 < 100ms

#### F-02 确定性执行引擎

- 按 YAML 步骤顺序执行，每步只做 YAML 声明的事，**不做任何智能猜测**
- 每步执行前后自动截图（可配置关闭）
- 每步结果写入上下文对象：成功/失败、耗时、提取的值、页面 URL/标题
- 支持每步自定义超时（全局默认 30s，元素等待 10s）
- 步骤间支持变量插值：`${ctx.userId}`（由前序步骤 extract 得到）

验收标准：
- [ ] 12 种核心步骤类型（goto/click/fill/select/check/hover/press/wait/extract/scroll/download/screenshot）全部实现并有单测
- [ ] 同一 Playbook 连续跑 10 次，结果一致性 100%（结果字段逐字段一致）
- [ ] 100 步 Playbook 跑完无内存泄漏（堆内存增量 < 50MB）

#### F-03 失败检测机制

失败被明确分类为 4 类，不同类别后续路由不同（见 F-05）：

| 失败类型 | 检测方式 | 示例 |
|----------|----------|------|
| E1 元素定位失败 | locator.waitFor 超时（默认 10s） | 按钮改名了、DOM 结构变了 |
| E2 页面状态异常 | URL 跟预期不符 / 弹窗遮挡 / 404 / 500 | 登录过期被踢到登录页、限流弹窗 |
| E3 超时 | 页面 load 超时 / 下载超时 / 整体任务超时 | 后台接口卡死 |
| E4 断言失败 | assert 步骤条件不成立 | 提交后没出现"成功"提示 |

验收标准：
- [ ] 4 类失败在测试站点 100% 被正确分类
- [ ] E2 页面状态异常必须在 3s 内被检测到（不能等满超时才知道挂了）
- [ ] 每次失败必须自动归档：失败截图 + 失败时 DOM 快照 + 失败步骤 ID（供兜底 Agent 和人工 review）

#### F-04 兜底 Agent 接管（视觉 + DOM 双通道）

失败发生时自动触发，无需人工干预：

1. 采集当前页面信息：全页截图 + 压缩 DOM 树（可见性/可交互性标注、role/label/text 属性）
2. VLM（Qwen-VL / GPT-4o，可配置）接收：截图 + DOM 摘要 + 失败上下文（哪个步骤、什么错误、任务目标）
3. Agent 每次决策一个原子动作（click/fill/press/back/wait/goto），执行后重新观察
4. 安全约束：白名单域名限制（Agent 不能把数据提交到任务外的网站）、危险操作二次确认（如删除、支付类动作在无人值守模式直接拒绝）、步数上限（默认 15 步）
5. 达到恢复点或任务目标 → 退出接管态

验收标准：
- [ ] 在改版的演示站点上（按钮迁移、弹窗新增、流程顺序微调），接管成功率 ≥ 70%
- [ ] Agent 每步决策耗时 < 8s（含截图 + VLM 推理）
- [ ] 安全约束 100% 生效：白名单外域名提交被拒绝、危险动作被拒绝（有测试用例）
- [ ] 接管全程有轨迹记录（每步截图 + 决策理由），供沉淀和审计

#### F-05 恢复点判定与回归 Playbook

Agent 每完成一个动作后，检查是否到达"恢复点"：

- **恢复点定义**：Playbook 后续某个步骤的"页面特征"（URL pattern + 关键元素存在性 + 关键文本）
- Agent 到达恢复点 → 记录"到达方式"（做了哪些操作）→ 跳回 Playbook 从该步骤继续
- 找不到恢复点：Agent 继续尝试（受步数上限约束），或向用户请求帮助（挂起等待或失败退出，按配置）

验收标准：
- [ ] 到达恢复点后，Playbook 续跑成功率 ≥ 95%
- [ ] 恢复点匹配必须在 500ms 内完成（不能拖慢 Agent 每步循环）
- [ ] 回归时上下文无缝衔接（前序提取的变量不丢失）

#### F-06 Playbook 自动沉淀

接管段结束（无论成败）后触发：

- Agent 轨迹中的每个动作 → 转换为等价 YAML 步骤（动作类型 + 选择器 + 参数）
- 插入/替换到 Playbook 中失败步骤所在的位置，生成新版本
- 新版本入库前：自动生成 diff 视图（人可 review）；可选 `--auto-promote` 跳过人工（默认关）
- 版本链管理：v1 → v2 → v3，任何版本可回滚

验收标准：
- [ ] 沉淀出的新 Playbook 二次运行成功率 ≥ 90%
- [ ] 生成的 YAML 通过 Schema 校验 100%
- [ ] 模板化场景（改按钮、加弹窗、改流程）各 10 次沉淀，生成 YAML 可读性人工评分 ≥ 4/5
- [ ] 版本回滚功能可用：`pbagent rollback <playbook> --to v1`

#### F-07 参数化

- CLI 支持 `--params '{"key": value}'` 与 `--params-file params.json`
- Playbook 内 `${params.xxx}` 插值；循环步骤（loop over 数组）支持批量操作
- 敏感参数（密码）支持从环境变量注入 `${env.PASSWORD}`，避免明文落盘

验收标准：
- [ ] 参数类型校验：缺参/类型不匹配给出明确报错（哪个步骤的哪个参数）
- [ ] 循环 50 个商品改价 E2E 测试通过
- [ ] 报告中敏感参数自动脱敏（日志/报告中显示为 `***`）

#### F-08 运行报告与可观测

- 每次运行生成结构化报告（JSON + HTML）：
  - 步骤明细：状态、耗时、截图路径、错误信息
  - 成本明细：LLM 调用次数、token 用量、费用估算（Playbook 模式为 $0）
  - 模式标注：每步属于 Playbook 执行 / Agent 接管
  - 模式切换时间线（A→B→A 的完整过程标注）
- 失败时报告包含归因：失败类型 + 修复建议
- 报告存本地，路径可追溯（runId 关联所有产物）

验收标准：
- [ ] HTML 报告步骤通过率、模式时间线、成本一目了然（演示截图素材）
- [ ] JSON 报告机器可读，字段稳定（供后续 dashboard 用）
- [ ] 任意运行可在 3 分钟内从报告回放定位到具体失败步骤（人工计时）

#### F-09 凭证管理

- 登录类 Playbook 支持登录一次、session 持久化复用（storageState 落盘）
- session 过期自动检测（跳登录页 = E2 失败）→ 触发 Agent 重新登录（或重新跑登录 Playbook）
- 凭证加密存储（AES-256-GCM，密钥来自环境变量或 keychain）
- 敏感字段（password、token）在日志/报告/Playbook 中自动脱敏

验收标准：

#### F-10 自然语言生成 Playbook 草稿（v1.0 内 P1）

# 5. 需求变更记录

## 变更 V2-1：Web 控制台改版为会话式交互（2026-09-14）

- **变更编号**：V2-1
- **提出人**：xiaopeng.chen（boss）
- **状态**：已交付（2026-09-14 端到端验证通过，验收项全勾）
- **影响范围**：Web 前端整体重构 + 后端会话模型 + 存储

### 5.1 变更背景

v1.0 Web 控制台是"单任务表单"模型：顶部导航 + 一次提交一个任务，任务结束即断。boss 在使用中发现：

1. **缺少多轮协作心智**：浏览器操作往往是连续的（先看列表 → 再改这条 → 再确认），单任务模型每次都要重新填表单，体验割裂
2. **历史任务与当前工作流脱节**：历史页只能"看"，不能"继续聊"
3. **视觉风格与工具调性不符**：蓝色渐变 + 浮夸阴影，与开发者工具的极简气质不符

### 5.2 需求描述（对齐 Codex 桌面端交互范式）

**整体布局**：

```
┌──────────┬────────────────────────────┐
│ 历史对话  │                            │
│ 列表      │   对话主区域               │
│          │   （默认：主页输入框）      │
│          │                            │
│──────────│                            │
│ ⚙ 设置    │                            │
└──────────┴────────────────────────────┘
```

- 左侧栏：历史对话列表（新建入口 + 会话卡片，点击切换）+ 左下角设置入口
- 右侧主区：默认主页（居中大输入框 + 沉淀流程快捷卡片）；进入会话后是对话流
- **视觉风格**：黑白灰极简（对齐 Codex 桌面端 / VS Code 暗色 / Linear 风格），去彩色渐变、去浮夸阴影

**会话与记忆功能**：

1. **会话（Session）**：一次"从输入框到任务完成"的完整交互是一个会话。会话有标题（首条消息摘要）、创建时间、消息流
2. **对话记忆**：同一会话内，用户可以继续追问（如"帮我把 S050 价格再改成 300"）。Agent 拿到：之前任务的 URL/参数/结果 + 会话内消息历史——**在同一起始 URL 域内**连续操作，不需要重新填表单
3. **消息流结构**：用户消息（自然语言指令）+ Agent 回复（任务执行结果卡：步骤时间线/截图/成本/总结）
4. **会话管理**：新建 / 切换 / 重命名 / 删除；列表持久化（服务端落盘），重启不丢

### 5.3 技术方案

| 层 | 方案 |
|----|------|
| 前端框架 | Vue3 + Vite（现有栈，不换） |
| 布局 | CSS Grid 两栏（左侧 260px 固定 + 右侧自适应），黑白灰主题变量 |
| 会话模型 | 服务端 Session{ id, title, createdAt, messages[] }，落盘 runs/web-sessions.json（结构对齐 web-history.json） |
| 对话记忆 | 会话内新指令提交时，后端把「会话历史摘要 + 上次任务上下文」注入 Agent 提示词（上轮 options + result 摘要 + 最近 N 条消息），LLM 在既有页面状态上继续操作 |
| API | GET /api/sessions、POST /api/sessions、DELETE /api/sessions/:id、PATCH /api/sessions/:id（重命名）、GET /api/sessions/:id/messages |
| SSE | 复用现有 /api/tasks/:id/events，会话视图订阅任务事件渲染到消息流 |
| 组件拆分 | App.vue（布局壳）→ Sidebar.vue（列表+设置入口）、HomeView.vue（主页输入框）、SessionView.vue（对话流）、MessageTask.vue（任务结果卡）、SettingsPanel.vue（设置抽屉/弹层） |
| 迁移兼容 | 旧 web-history.json 保留不动；新会话模型并行。TaskForm/TaskRun 的核心逻辑（参数收集、SSE 消费、时间线渲染）迁移进新组件 |

### 5.5 已知限制（V2-1 实测发现）

- **凭证不进会话记忆**：上轮 Playbook 模式的凭证（${env.*} 注入）对追问轮 Agent 不可见。实测：追问轮 Agent 需自行摸索登录（本次靠页面提示自救成功，耗 31 次 LLM 调用）。修复方向：会话记忆补凭证槽位（脱敏存储）或追问轮优先路由回 Playbook（selectPlaybook 前置）
- 会话内暂不能直接运行沉淀流程（顶部"⚡ 沉淀流程"仅展示；快捷运行走主页）——v2.1 候选
